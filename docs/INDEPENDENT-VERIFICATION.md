## 2. 复核中抓出的 6 个真缺陷（全部已修 + 补回归测试）

这一节的每一条都是**先复现、再定位、再修、再验证**，不是"顺手改改"。

### D1 引用（回复）内容**端到端显示不出来** —— 三处同时断链

- **现象**：库里 27 条引用消息，**27/27 的被引用消息都在库中**，却一条都显示不出引用了什么。
- **根因**（三处叠加）：
  1. 详情接口用 `typeof message.replyToId === 'number'` 判断，而 `replyToId` 是 QQ 的原始字符串 id → **恒为 false**，预览永远 `null`；
  2. 时间线接口从不返回 `replyPreview`，前端 `replyPreviewOf()` 的三个候选字段全都取不到；
  3. 前端点击"点击加载"时把 QQ 原始 id 当本库 id 去请求 → 实测 **404**（`{"error":"消息不存在"}`）。
- **修复**：`Db.getReplyPreviews()` 批量解析（会话内 `msg_key` 优先、`msg_id` 兜底，两种形态都支持），时间线与详情都返回 `replyPreview` / `replyToMessageId`，前端改用内部 id。
- **验证**：真实库 27/27 解析成功、同会话隔离成立、文本逐条相等；浏览器里实拍到"↩ 示例账号：这是一条示例消息"；点击引用目标 `GET /api/messages/2` → **200**（原先 404）。
- **回归测试**：`tests/reply-preview.test.ts`（15 例）。

### D2 磁盘上有备份，网页说"尚无备份记录"，且这些备份**永远不会被清理**

- **现象**：`data/backups/` 里躺着 2 份带 manifest 的快照，`backups` 表 **0 行** → 网页显示"尚无备份记录"，保留策略（`keep`）也永远数不到它们。
- **根因**：快照用 `VACUUM INTO` 生成，而它的登记行是在快照**之后**写进当前库的 —— 快照不可能包含自己那一行。一旦用这份快照做过恢复（恢复 = 快照替换当前库），那次备份的记录就消失了。`pruneBackups()` 只遍历表里的行 → **孤儿快照在磁盘上无限堆积**。
- **修复**：新增 `reconcileBackups()` 以文件系统为准对账（元数据取同名 manifest，缺 manifest 时按文件名 + mtime 兜底），并接到 `/api/backups` 与 `pruneBackups()` 之前。
- **验证**：清空表后调接口 → 2 份快照带真实 `kind`/`createdAt`/`sizeBytes`/`messageCount` 全部登记回来；浏览器里备份面板从"尚无备份记录"变成"成功 · 2026-10-13 13:26:36 · 1.1 MB · 282 条 / 25 个"。
- **回归测试**：`tests/backup-reconcile.test.ts`（8 例，含用**真实 `createBackup` 产出**的 manifest 做输入）。

### D3 数据目录一搬走，备份记录就会**重复**

- **现象**：我自己写的 D2 修复，在把 `data/` 复制到别处后立刻暴露了：同一个快照被登记了**两行**（老行路径失效 → 新路径又被当新快照）。
- **影响**：这正是任务书里的"设备更换 / 部署到服务器"场景 —— 换机后备份列表会出现同名重复项，保留份数算错。
- **修复**：按**文件名**认领，老行**改指**到新位置（`repointBackup`），不再补新行。
- **回归测试**：`tests/backup-reconcile.test.ts` 的"数据目录整体搬迁后不产生重复记录"用例（8 例中的 1 例）。

### D4 网页"运行日志与错误"永远是空的（`dbSink` 从没接上）

- **现象**：`logs` 表、`/api/logs`、网页日志页都在，但 `SELECT COUNT(*) FROM logs` **恒为 0**。
- **根因**：`Logger` 的 `dbSink` 参数早就写好、`logger.ts` 里也真的会调用它，但**全仓没有任何调用点传它**（`apps/cli/src/main.ts` 里甚至留着一行注释"日志落库"，代码却没写）。
- **修复**：在 CLI 组装 logger 时接上 sink（`scope` 为 `db*` 的不落库，避免数据库自身出错时递归）；并把 CLI 采集端不可用这条失败也记进日志 —— 原先它只 `stderr.write`，终端滚走就再也查不到"为什么某一轮没采到"。
- **修复后失败记录也能被单独列出**（`tests/log-sink.test.ts` 全部用例）。
- **回归测试**：`tests/log-sink.test.ts`（6 例，**真实子进程**验证 —— 因为缺陷恰好在"接线"上，只测 `Logger` 单测在修复前也会全绿）。

### D5 数据库日志没有保留策略（`pruneLogs` 零调用）

- **现象**：`Db.pruneLogs(keepDays)` 定义了却没有任何调用点，数据库日志只增不减。
- **修复**：新增配置段 `logs.dbKeepDays`（默认 30，`0` = 不清理，支持 `QQ_ARCHIVE_LOG_KEEP_DAYS` 覆盖），启动时执行一次清理；`config.example.json` 已同步说明。
- **验证**：插一条 40 天前 + 一条 3 天前的日志 → 跑任意命令 → **只剩 3 天前那条**；`keepDays=0` 时 400 天前的也不动。
- **回归测试**：`tests/log-sink.test.ts`（含环境变量覆盖与非法值校验）。

### D6 采集窗口重叠导致**媒体每轮被重新下载**

- **现象**：真实采集日志里每轮都是 `mediaSaved=2` —— 同一张图/同一段视频每隔 60 秒被重新下载一次。
- **根因**：窗口重叠（`lookbackSec=300`）是常态，重复**消息**被唯一约束挡住，但**媒体**没有这道闸门。
- **影响**：长期挂机时白白消耗带宽与上游压力（不是正确性问题，但正是"长期运行"会咬人的地方）。
- **修复**：`handleMedia()` 先查"这条消息已关联的 `present` 媒体数是否 ≥ 本条引用数"，齐备则跳过。
- **安全性质（重点）**：只数 `present` —— 缺失/损坏的媒体**下一轮必须仍然重试**，所以直链 rkey 过期后的补救路径不受影响；查询失败时按"未知"处理照常下载，绝不因一次读失败漏掉媒体。
- **验证**：真实 NapCat 连跑两轮，`媒体：保存 0`（原先每轮都是 2）；以及回归测试里显式验证"媒体转成 missing 后必须重新尝试"。
- **回归测试**：`tests/collect.test.ts` 用例 7b。

### D10 停机会被连接拖住（**有界停机**，含一次未能解释的实测）

- **现象**：一次重启操作里，正在运行的实例收到 `SIGTERM` 后 **20 秒仍未退出**（最后只能 `kill -9`）。
- **诚实说明**：我**没能复现**出那次挂起。隔离环境下试了四种情形 —— 空闲 keep-alive 连接、在途大媒体流（慢读者不读完）、只发一半请求体的请求、采集中每 5 秒一轮 —— **全部都在 1 秒内干净退出**。
- **处理方式**：不去假装能修一个复现不了的根因，而是**把停机改成有界的**：`SIGTERM` 后给 10 秒优雅期（`QQ_ARCHIVE_SHUTDOWN_GRACE_MS` 可调），超时就强制断开剩余连接并在 0.5 秒后退出。这样无论进程里挂了什么，停机时间都可预期，systemd 不必靠 90 秒的 `TimeoutStopSec` 去 SIGKILL。
- **回归测试**：`tests/cli.test.ts` 的"收到 SIGTERM 后必须在宽限期内退出"用例 —— 守的是**结果**（有界），不是那个复现不了的根因。**这一条是我没有完全查清的问题，如实列在这里。**

| # | 位置 | 症状 | 修复 |

## 7. 追加：采集过滤（`filters`）与"和 NapCat 功能对比"

### 7.1 先说清楚：本系统**不是** NapCat 的替代品

NapCat 是完整的 QQ 机器人框架（OneBot 11/12 协议实现 + 几百个接口，能发消息、管群、踢人、改名片……）。
本系统**刻意只用它的只读子集**，这不是能力不足，是三条硬约束下的选择：

| 约束 | 说明 |
| --- | --- |
| 账号安全 | 写接口（发消息/删消息/踢人）意味着"程序可能替你在群里说话"。一个防丢失归档工具不该有此能力 |
| 许可证 | NapCat 是**自定义许可**（禁商用、禁发布修改版）。只通过网络调用公开 HTTP 接口属于互操作，不分发、不修改、不打包 |
| 可替换性 | 只要实现 OneBot v11 的只读接口（NapCat / LLOneBot / …），采集端就能换 |

代码里这条边界是**硬编码的最后一道闸**：`READ_ONLY_ACTIONS` 白名单之外的动作在本地直接拒绝，
**连 HTTP 请求都不会发出**（`packages/collect/src/onebot.ts`）。白名单共 11 个：
`get_login_info` / `get_status` / `get_version_info` / `get_group_list` / `get_friend_list` /
`get_group_msg_history` / `get_friend_msg_history` / `get_forward_msg` / `get_image` / `get_record` / `get_file`。

### 7.2 登录方式：扫码 + 快捷登录有，**账号密码没有**（也不是本项目的选择）

实测当前实例（`GET /api/napcat/status`）：

```json
{"configured":true,"webuiUrl":"http://127.0.0.1:6099","connected":true,"isLogin":true}
GET /api/napcat/accounts → [{"uin":"1000000001","nickname":"…","isQuickLogin":true}]
POST /api/napcat/qrcode  → {"isLogin":true,"uin":null,"png":null}   # 已登录时不发二维码
```

已支持：**扫码登录**（二维码在网页显示 / 终端渲染，轮询登录态）、**快捷登录**（用本机已保存的登录态，不用扫码）。
账号密码登录（QQ 号 + 密码）：**不支持，且 NapCat 本身也没有这个接口** —— 这一点我不是靠猜，
而是查了本地那份最完整的 NapCat 驱动项目（`qq-chat-exporter` 的 Rust 驱动）实际调用的端点：

```
/api/auth/login                （WebUI 自身的令牌认证）
/api/QQLogin/GetQQLoginQrcode  （取二维码）
/api/QQLogin/CheckLoginStatus  （轮询登录态）
/api/QQLogin/GetQuickLoginListNew / GetQuickLoginList（已保存账号）
/api/QQLogin/SetQuickLogin     （快捷登录）
```

没有 password 登录端点。腾讯早已不支持第三方客户端用密码直登（设备锁/验证码/风控），
所以"支持账号密码登录"这条**做不到**，不是没实现。

### 7.3 新增：采集过滤（本次追加实现）

原来的系统**没有任何过滤能力**（只有"只采集哪些会话"的白名单）。现在补上了 `filters` 段：

| 规则 | 语义 |
| --- | --- |
| `excludeKeywords` | 子串匹配，大小写不敏感 |
| `excludeSenders` | 与 QQ 号 / uid / 昵称**精确相等** |
| `excludeTypes` | 与消息类型精确相等（text/image/video/audio/file/forward/reply/system/json/other） |

**最关键的设计决定：默认只标记、不丢弃。** 命中规则的消息照样入库，只是打上 `filtered` + 命中理由，
默认不在时间线/搜索里显示；勾选「包含已过滤消息」就能看到，**导出永远带上它们**。
真正跳过存储需要显式 `drop: true`。理由很直接：这是防丢失系统，过滤只该让人"少看点"，不该变成"少存点"。

实测证据（真实 NapCat，309 条消息一轮）：

```
一轮采集完成：会话 13｜拉取 309｜新增 309｜重复 0｜失败 0     ← 全部入库，一条没丢
库内：messages 总数 = 309，其中被标记 = 1
标记样例：#262 「这是一条示例消息」 | 关键词命中「微信」
```

浏览器实测：勾选「包含已过滤消息」后，该消息出现并带橙色徽标
`已过滤：关键词命中「微信」`，时间线标题显示 `含已过滤 1`；不勾选时它不出现。

配套 `qq-archive refilter`：改规则后对**已有消息**重算标记（表结构加了 migration 6 的两列）。
实测：同规则重跑 = 0 改动（幂等）；换规则 = 旧标记取消 + 新命中标记（可逆）；
关掉过滤再跑 = 清空标记且**消息一条不少**（310 → 310）。

> 这一节也顺带暴露并修掉了我**自己代码里的两个缺陷**：过滤计数没进轮次日志、以及
> `refilter` 命令漏登记进命令白名单（表现是打印整篇用法而不是执行）——
> 第二个是真实运行时才发现的，单测覆盖不到"命令名是否注册"。

### 7.4 部署到服务器：Windows / Linux

| 环境 | 支持情况 | 证据 |
| --- | --- | --- |
| **Linux（Debian/Ubuntu/Arch）** | **支持且已实测** | 本机 CachyOS（Arch 系）上正在跑：`node:sqlite` + `node:http`，生产依赖 0 个；systemd unit 在 `deploy/` |
| **Linux 服务器长期运行** | **支持**，但**未在真实 systemd 上验证过** | unit 文件与文档齐备；采集端即使与服务器分离也能跑（先归档再同步） |
| **Windows** | **源码可跑**（Node 原生跨平台），但**脚本未在真实 Windows 上执行过** | `deploy/windows/` 有启动/安装脚本，只做了 80 项静态自检；本机无 `pwsh`，无 Windows 环境 |
| **Docker** | **未提供** | 本机没装 docker，不交付未验证的东西 |

采集端与归档端可以**分开部署**：服务器上没有能稳定运行 QQ 客户端的环境时，
在个人电脑上跑采集端，再把已归档的数据同步到服务器（见 `docs/DEPLOYMENT.md` 第 5 节）。
但要明确：**服务器上登录了 QQ ≠ 拿到了手机端的全部历史**，界限见第 1 节。
